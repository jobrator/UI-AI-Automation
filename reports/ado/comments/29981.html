Retest — 2026-08-19 — STILL FAILING

Retested against production POST https://api.jobrator.com/api/login. Note the request contract has changed since this bug was filed: a loginMethod field (enum email|google) is now required, and profile now accepts Candidate|Company. Both scenarios were re-run with the corrected payload.

Scenario 1 — internal exception code still leaked: FAIL
Registered candidate email + wrong password:
HTTP 401
{"message":"Invalid credentials or profile",
 "exception":"E_INVALID_AUTH_PASSWORD: Password mis-match"}
The exception field is still present and still reveals the internal error code. Partial improvement: message is now generic ("Invalid credentials or profile").

Scenario 2 — responses still distinguishable: FAIL
Registered email + wrong password  -> 401 {"message":"Invalid credentials or profile",
                                            "exception":"E_INVALID_AUTH_PASSWORD: Password mis-match"}
Unregistered email + any password   -> 401 {"message":"Invalid credentials or profile",
                                            "exception":"User not found or account disabled"}
Status codes match, but the bodies are not byte-identical. The exception value alone distinguishes "this account exists, wrong password" from "no such account" — the enumeration oracle is intact.

Verdict: Not fixed. Remove the exception field from authentication failure responses (or make it constant across all failure modes) so the two cases are indistinguishable.
