5. Investigation: the VNIN skips are masking a production defect

TC_VN002 / TC_VN005 — reclassify from "environmental" to P1 defect

Both scenarios skip with the justification that they need a real, NIMC-registered VNIN, implying an unavoidable test-data gap. Live network capture of the submit disproves that.

Clicking Verify produces exactly one network request:

POST https://payarenaverification.com/api/account/token → 200 {"success":true,"description":"Successful", "data":{"auth_token":null,"access_tokenexpire":"..."}} UI result: "Failed — VNIN Verification failed"
  • The VNIN number is never transmitted — no lookup request is ever made.
  • The flow dies at token acquisition because the provider returns auth_token: null alongside success: true.
  • Therefore a genuine registered VNIN would fail identically. VNIN verification is broken for every user in production.
  • TC_VN005 is collateral: its precondition can never be met while TC_VN002 cannot pass.

Two further issues found during the same investigation

  • Credential exposure (security). The token request ships the verification provider's admin username and password in plaintext from the browser, readable by any visitor via devtools. This is independently reportable, and plausibly explains the null token if those credentials were rotated after leaking.
  • TC_VN003 is a false green. It asserts "invalid VNIN → error message" and passes — but the error it observes comes from the broken integration, not from VNIN validation. It would pass with a valid VNIN too, so it currently proves nothing.

Test-side defects in TC_VN005 itself

  • Its final Then logs a warning and asserts nothing — the scenario could never fail even with the precondition met.
  • The precondition checks for the badge on the VNIN page, before the When navigates to the dashboard where the badge would appear.
  • The selector *:has-text("Verified") matches ancestors up to <html>, so it can false-positive on any page containing that word.

TC070 / TC071 / TC072 — AI CV generation (BUG-015)

The AI endpoint proxies to Google Gemini 2.5 Flash. When the model replies 503 Service Unavailable, Jobrator neither retries nor degrades — it returns 500 and the UI shows a dead-end "Error writing via AI" modal that discards the user's typed input.

POST https://api.jobrator.com/api/account/ai/generate → 500 {"message":"Failed to generate text", "error":"[GoogleGenerativeAI Error]: ... gemini-2.5-flash:generateContent: [503 Service Unavailable] This model is currently experiencing high demand. Spikes in demand are usually temporary. Please try again later."}
  • Intermittent, roughly 1 attempt in 3. A three-attempt probe gave 500 / 200 / 200; a sequential re-run of the three scenarios gave 2 failed / 1 passed. The endpoint is wired correctly — the defect is purely the unhandled upstream 503.
  • This is a paid, subscription-gated feature failing for a third of attempts, with no retry button and no preservation of what the user typed.
  • Secondary: the 500 body forwards Gemini's raw error verbatim, disclosing the model, provider and upstream URL to the client.

6Investigate the four flaky scenarios under parallelism (TC_EREG012, TC_ACC006, TC_AJP002, TC_REG005) — all passed sequentially, so the suite's parallel: 2 setting is the likely factor.QAP3
